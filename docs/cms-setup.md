# ระบบหลังบ้าน `/admin` — คู่มือ

ลูกค้าแก้เนื้อหาเว็บได้เองโดยไม่ต้องแตะโค้ด: เพิ่ม/แก้/ลบสินค้า บทความ ผลงาน
คำถามที่พบบ่อย และหมวดหมู่ · แก้ข้อมูลบริษัท เมนู และเนื้อหาหน้าแรก · อัปโหลดรูป

---

## แนวคิดที่เลือกใช้ และเหตุผล

### เนื้อหามีโครงสร้างอยู่แล้ว → ย้ายขึ้นฐานข้อมูลทั้งหมด

เนื้อหาของเว็บนี้อยู่ในไฟล์ `src/data/*.ts` ซึ่ง **มีโครงสร้างชัดเจนอยู่แล้ว**
ไม่ใช่ HTML เขียนมือ จึงย้ายขึ้นเป็นตารางจริงใน Supabase ได้ตรงๆ

ผลคือลูกค้า **เพิ่มและลบสินค้า/บทความ/ผลงานได้เอง** ไม่ใช่แค่แก้ข้อความที่มีอยู่
ซึ่งเป็นสิ่งที่ระบบหลังบ้านแบบ "ทับข้อความบน HTML เดิม" ทำไม่ได้

### ไฟล์ `src/data/*.ts` ยังอยู่ในฐานะค่าสำรอง

ไม่ใช่ขยะที่ลืมลบ — ถ้า Supabase ล่มหรือ deploy โดยไม่ใส่ env เว็บจะยังขึ้นครบ
ทุกหน้าด้วยเนื้อหาชุดตั้งต้น แทนที่จะจอขาว

`npm run cms:verify` เทียบเนื้อหาใน DB กับไฟล์เหล่านี้ทีละรายการแบบ deep-equal
ยืนยันว่าถอยไปใช้แล้วเนื้อหาไม่เพี้ยน

## ร่าง vs เผยแพร่

ทุกอย่างมีสองสถานะเหมือนกันหมด

| | เก็บที่ไหน | เว็บจริงเห็นไหม |
|---|---|---|
| **บันทึกร่าง** | คอลัมน์ปกติ / `draft_value` | ไม่เห็น |
| **เผยแพร่** | `published` (jsonb) / `published_value` | เห็น |

สแนปช็อตที่เผยแพร่สร้างโดยฟังก์ชันในฐานข้อมูล (`private.*_snapshot`) ซึ่งเป็น
ตัวเดียวกับที่ใช้ตอนย้ายข้อมูลเข้าครั้งแรกและตัวเดียวกับที่ธง `has_draft` ใช้คำนวณ
ทั้งสามอย่างจึงไม่มีทางหลุดจากกันเพราะลืมแก้ที่ใดที่หนึ่ง

**ตรวจแล้วว่าทำงานจริง** — บันทึกร่างแล้ว build ใหม่ ไม่พบข้อความฉบับร่างในไฟล์
ที่ build ออกมาเลยแม้แต่ไฟล์เดียว · กดเผยแพร่แล้ว build ใหม่ เนื้อหาถึงจะเปลี่ยน

|---|---|---|

| สินค้า | `/admin/products` | สินค้า 11 รายการแยกตามหมวด · **เพิ่ม / แก้ / ลบ** ครบทุกฟิลด์ |
| | `/admin/categories` | หมวดหมู่สินค้า · เรียงลำดับ · กันลบหมวดที่ยังมีสินค้าอยู่ |
| บทความ | `/admin/articles` | บทความ · **เขียนใหม่ / แก้ / ลบ** พร้อมเติมวันที่ไทยอัตโนมัติ |
| ข้อความในหน้าเว็บ | `/admin/copy` | **จอแก้ไขแบบเห็นหน้าเว็บจริง** — ทุกข้อความและทุกรูปของ 19 หน้า รวม 1,275 จุด |
| คลังรูป | `/admin/media` | คลังรูป — รูปเดิมของเว็บ + ที่อัปโหลดใหม่ |
| ตั้งค่าเว็บไซต์ | `/admin/settings` | ข้อมูลบริษัท · เบอร์ · อีเมล · LINE · ที่อยู่ · เวลาทำการ |
| | `/admin/menu` | เมนูหลักพร้อมเมนูย่อย · มาตรฐาน (พร้อมรูปและเนื้อหาหน้า `/standards`) · ตัวเลขสถิติ |
| | `/admin/home` | การ์ดหมวด · จุดเด่น · โลโก้ลูกค้า · ขั้นตอนการทา · บล็อกข้อกฎหมาย |
| | `/admin/projects` | แกลเลอรีผลงาน · สลับลำดับ |
| | `/admin/faqs` | คำถามที่พบบ่อยท้ายหน้าแรก |
| | `/admin/services` | สองหน้าใต้เมนู "รับรองสีกันไฟ" |

## ตั้งค่าครั้งแรก

> **โปรเจคนี้ทำครบทุกข้อแล้ว** (Supabase project ref `joxozwjhqkraafostdbd`)
> ส่วนนี้เก็บไว้สำหรับตอนย้ายไป project ใหม่

### 1. รัน migration

Supabase Dashboard → SQL Editor → รันไฟล์ใน `supabase/migrations/` **ตามลำดับเลข**

สร้างให้: ตาราง `products` `categories` `articles` `projects` `faqs` `services`
`site_copy` `site_settings` `media` `cms_users` `content_revisions` พร้อม RLS ครบทุกตาราง,
storage bucket `media`, ฟังก์ชันสแนปช็อต และ RPC `cms_publish` / `cms_publish_all`

### 2. ตั้ง environment variables

ใส่ทั้งใน `.env.local` และใน Vercel (Settings → Environment Variables)

```
NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=sb_publishable_...
```

> ไม่ต้องใช้ service role key — ทุกอย่างวิ่งผ่าน publishable key + RLS

### 3. สร้างผู้ใช้

Authentication → Users → **Add user** (อีเมล + รหัสผ่าน, ติ๊ก Auto Confirm User)

จากนั้นให้สิทธิ์เข้าหลังบ้านใน SQL Editor:

```sql
insert into public.cms_users (id, email, display_name, role)
select id, email, 'ชื่อที่จะให้แสดง', 'editor'
  from auth.users where email = 'อีเมลที่เพิ่งสร้าง';
```

**ล็อกอินผ่านอย่างเดียวยังเข้าไม่ได้** ต้องมีแถวใน `cms_users` ด้วย
ป้องกันกรณีมีคนสมัครเข้ามาเอง

### 4. ย้ายเนื้อหาเข้าฐานข้อมูล

```bash
CMS_EMAIL=... CMS_PASSWORD=... npm run cms:seed
npm run cms:verify
```

`cms:seed` เขียนผ่านสิทธิ์ของผู้ใช้หลังบ้านจริง ไม่ใช่ service role key —
ถ้ามันรันผ่าน ก็แปลว่าสิทธิ์ของทีมงานถูกตั้งไว้ถูกต้องจริง ไม่ใช่ผ่านเพราะข้ามด่านไป

## ความปลอดภัย

- **RLS เปิดทุกตาราง** และ `anon` ถูกถอนสิทธิ์คอลัมน์ฉบับร่างทั้งหมดในระดับคอลัมน์
  ต่อให้ยิงตรงเข้า REST API ก็เห็นเฉพาะเนื้อหาที่เผยแพร่แล้ว
  (`cms:verify` ยิงทดสอบ 9 คอลัมน์ ได้ `42501` ทุกข้อ)
- **Supabase security advisor: 0 ข้อ**
- ฟังก์ชัน `cms_publish` เป็น **security invoker** โดยตั้งใจ (ไม่ใช่ definer)
  เพราะสิทธิ์ที่จำเป็นมีอยู่แล้วในบทบาท `authenticated` การใช้ definer จะเพิ่ม
  ผิวสัมผัสโดยไม่จำเป็น
- ประตูกั้นสองชั้น: `src/proxy.ts` กันคนที่ยังไม่ล็อกอิน และ `(dash)/layout.tsx`
  กับทุก server action (`withCms`) ตรวจซ้ำว่ามีแถวใน `cms_users` จริง
  — server action ยิงตรงได้โดยไม่ผ่าน layout การเช็คที่ layout จึงเป็นแค่เรื่อง UI

## ข้อควรรู้สำหรับนักพัฒนา

### 1. แคชของ Next กับการ deploy

Next เก็บผลลัพธ์ `fetch` ที่เกิดตอน prerender ลง Data Cache และ Vercel เอาแคช
ก้อนนั้นกลับมาใช้ข้าม deploy **ผลคือ deploy ครั้งถัดไปจะ prerender ด้วยเนื้อหาเก่า
ทั้งที่ลูกค้ากดเผยแพร่ไปแล้ว** — เจอจริงระหว่างทำ (build ซ้ำได้เนื้อหาเดิม
จนกระทั่งลบ `.next/cache` ทิ้ง)

แก้โดยแนบ header `x-cms-build` ที่เปลี่ยนทุก deploy ใน `src/lib/supabase/public.ts`
กุญแจแคชของ deploy ใหม่จึงไม่ชนกับของเดิม

**อย่าเปลี่ยนไปใช้ `cache: "no-store"`** — ลองแล้ว Next เปลี่ยนทุกหน้าเป็น dynamic
และในโค้ดนี้ error จะถูกกลืนแล้วถอยไปใช้เนื้อหาตั้งต้นแบบเงียบๆ

### 2. Next 16

เปลี่ยน `middleware.ts` เป็น `proxy.ts` และแทนที่ `unstable_cache` ด้วย `use cache`
โปรเจคนี้ไม่ใช้ `use cache` — หน้าเว็บเป็น static แล้วสั่ง `revalidatePath` ตอนกดเผยแพร่แทน

### 3. ล้างแคชแบบเหมารวมโดยตั้งใจ

`revalidateSite()` เรียก `revalidatePath("/", "layout")` ล้างทั้งเว็บ ไม่ได้ไล่ระบุ
ทีละ path เพราะข้อมูลชิ้นเดียวโผล่หลายหน้าพร้อมกัน (สินค้าตัวเดียวอยู่ทั้งหน้าแรก
หน้าหมวด หน้าสินค้า และหน้าบริการ) การไล่ระบุจึงพลาดง่ายและพลาดแบบเงียบๆ
เว็บนี้มี 42 หน้า สร้างใหม่ทั้งหมดถูกกว่าการมีหน้าที่ข้อมูลค้าง

### 4. รูปที่แก้จากหลังบ้านได้

รูปที่มากับเนื้อหา (สินค้า บทความ ผลงาน หมวดหมู่ การ์ดหน้าแรก โลโก้ลูกค้า
รูปมาตรฐาน หัวหน้าบริการ) แก้ได้ที่หน้าจอของมันเอง

ส่วนรูปที่ฝังใน JSX — สไลด์หน้าแรก การ์ดคู่ใต้แบนเนอร์ แถบ "เกี่ยวกับเรา"
รูปข้าง FAQ โลโก้ และรูปทุกใบในหน้า landing — ใช้ `<CmsImage>` แทน `next/image`
**กุญแจคือ path เดิมของรูปนั้น** เก็บส่วนที่ถูกทับไว้ในค่าตั้งค่า `images`
คลิกรูปในจอพรีวิวแล้วเลือกรูปใหม่จากคลังรูปได้ทันที

เลือก path เป็นกุญแจเพราะอ่านออกทั้งในฐานข้อมูลและในหลังบ้าน · ไม่เลื่อนเมื่อ
เพิ่ม/ลบรูป · และถ้าเปลี่ยนรูปในโค้ด ค่าที่ลูกค้าเคยเลือกจะเลิกมีผลไปเอง
เพราะกุญแจเดิมไม่มีอยู่บนหน้าแล้ว จึงไม่ต้องเก็บ hash เหมือนฝั่งข้อความ

ผลข้างเคียงที่ตั้งใจ: รูปเดียวกันที่ใช้หลายหน้า เปลี่ยนทีเดียวเปลี่ยนพร้อมกันหมด

### 5. ข้อความประจำหน้า (`/admin/copy`)

หน้า landing ทั้ง 5 หน้าเก็บข้อความไว้ใน `src/data/*-lp.ts` เป็นก้อน object อยู่แล้ว
จึงไม่ต้องรื้อ JSX เลย — อ้างอิงแต่ละจุดด้วย **เส้นทางในก้อนนั้น**

```
hero.title · faqs.2.a · quoteForm.fields.3.options.1 · meta.ogTitle
```

ต่างจากการไล่เลข `t01 t02` ตรงที่กุญแจผูกกับ *ความหมาย* ไม่ใช่ *ลำดับ* —
เพิ่มย่อหน้าใหม่ตรงกลางแล้วกุญแจของย่อหน้าอื่นไม่เลื่อนตาม

หน้าเว็บดึงผ่าน `copyFor("neocoat")` ซึ่งคืน object หน้าตาเหมือน namespace ของไฟล์
ต้นฉบับเป๊ะ หน้าจึง destructure ชื่อเดิมออกมาใช้ได้เลยโดยไม่ต้องแก้ JSX

**ฐานข้อมูลเก็บเฉพาะจุดที่ต่างจากโค้ด** แก้กลับไปเหมือนเดิมเมื่อไหร่ แถวนั้นถูกลบทิ้ง
เปิด `/admin/copy` จึงตอบได้เสมอว่าลูกค้าแก้อะไรไปบ้าง

**กันข้อความไปโผล่ผิดที่** — ตอนบันทึกจะเก็บ hash ของข้อความตั้งต้นไว้ด้วย ถ้านักพัฒนา
แก้ข้อความในโค้ดทีหลังจนไม่ตรงกัน ระบบจะไม่ทับ แต่แสดงค่าจากโค้ดแทน และขึ้นคำเตือน
ในหน้าแก้ไขให้ลูกค้ากดยืนยันอีกครั้ง

**คีย์ที่เป็นโครงสร้างถูกกันไว้ไม่ให้แก้** — `href` `src` `id` `name` `kind` `type`
`slug` `icon` `topicField` และค่าที่ขึ้นต้นด้วย `/` `#` `http` เพราะถ้าแก้ได้
ลูกค้าจะทำลิงก์พัง ฟอร์มส่งไม่ออก หรือ anchor เลื่อนไปผิดที่โดยไม่รู้ตัว

นับจำนวนจุดได้ด้วย `node scripts/copy-count.mts`

### 6. จอแก้ไขแบบเห็นหน้าเว็บจริง

กด `/admin/copy` → เลือกหน้า → ได้จอสองฝั่ง ซ้ายคือ **หน้าเว็บตัวจริง** (ไม่ใช่ภาพจำลอง)
ขวาคือช่องกรอกของทุกจุดในหน้านั้น คลิกฝั่งไหนก็เด้งไปหาอีกฝั่ง พิมพ์ปุ๊บซ้ายเปลี่ยนปั๊บ

กลไก:

1. `/api/admin/preview?path=…` เปิด **Draft Mode** ของ Next (เช็ค `cms_users` ซ้ำในตัว route)
2. หน้าเว็บถูกเรนเดอร์ใหม่ด้วย *ฉบับร่าง* แล้ว `applyCopy(..., mark: true)` ห่อทุกข้อความ
   ด้วย `U+2062 INVISIBLE TIMES` เป็น `⁢กุญแจ⁢ข้อความ⁢`
3. `PreviewBridge` ในหน้าถอดเครื่องหมายออกแล้วห่อเป็น `<span data-cms-key>` ที่กดได้
   ส่วนรูปใช้ `data-cms-image` ที่ `CmsImage` ติดให้ตั้งแต่ฝั่งเซิร์ฟเวอร์
4. สองฝั่งคุยกันด้วย `postMessage` — `cms:select` / `cms:update` / `cms:focus`
   และคู่ `-image` ของมัน

**ผู้เข้าชมทั่วไปไม่เคยได้รับเครื่องหมายนี้** เพราะไม่มีคุกกี้ Draft Mode และต่อให้
ตั้งคุกกี้เองก็ยังอ่านฉบับร่างไม่ได้ เพราะ RLS กันคอลัมน์ `draft_*` ไว้อีกชั้น
ตรวจแล้วว่าหน้าสาธารณะมีเครื่องหมาย 0 ตัว และไม่มี `data-cms-image` ติดไปด้วย

หน้าที่เข้าระบบนี้แล้ว — ดู `COPY_PAGES` ใน `src/lib/cms/copy-pages.ts`:
หน้าเว็บหลัก 11 หน้า · หน้าที่ใช้โครงร่วมกัน 3 แบบ (หน้าสินค้า/บทความ/บริการ) ·

ข้อความของหน้าในกลุ่ม `(site)` ถูกยกออกจาก JSX มาไว้ใน `src/data/pages/*.ts`

### 7. `HTTP ERROR 431` ตอนรันบนเครื่องตัวเอง

เบราว์เซอร์ใช้ **ตะกร้าคุกกี้ใบเดียวกันสำหรับ `localhost` ทุกพอร์ต** โปรเจกต์อื่นที่เคย
รันบนเครื่องเดียวกันจึงทิ้งคุกกี้สะสมไว้ในตะกร้าเดียวกับเว็บนี้ พอรวมกันเกิน 16 KB
(ค่ามาตรฐานของ Node) เซิร์ฟเวอร์จะตอบ `431 Request Header Fields Too Large`
ก่อนที่โค้ดของเราจะได้ทำงานเลยแม้แต่บรรทัดเดียว

ไม่ใช่ปัญหาของเว็บนี้ — คุกกี้ของเราเองมีแค่ก้อนเดียวคือ session ของ Supabase
ราว 3 KB (ก้อน JSON 2.2 KB เข้ารหัส base64 แล้วหั่นเป็น `sb-…-auth-token.0/.1`)
บวกคุกกี้ Draft Mode ตอนพรีวิวอีกนิดหน่อย

ทั้ง `npm run dev` และ `npm start` จึงขยายเพดานเป็น 64 KB ผ่าน
`NODE_OPTIONS=--max-http-header-size=65536` ใน `package.json`

**บน production ไม่ต้องทำอะไร** เพราะโดเมนจริงมีตะกร้าคุกกี้ของตัวเอง มีแต่คุกกี้
ของเว็บนี้ ~3 KB ไม่เคยเฉียดเพดาน และ Vercel ไม่ได้เรียก `npm start` อยู่แล้ว

ถ้ายังเจอ 431 อีก แปลว่าตะกร้าโตเกิน 64 KB — ล้างคุกกี้เฉพาะ `localhost` ทิ้ง
(Chrome → กดไอคอนหน้า URL → Cookies and site data → Manage on-device site data)
ล้างแล้วจะหลุดจากระบบหลังบ้าน ล็อกอินใหม่ได้ตามปกติ
